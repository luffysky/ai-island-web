# Cron 怎麼排

不要所有來源都每分鐘爬，網站會封你，自己帳單也會先跳樓。

建議：

| 來源類型      |          頻率 |
| --------- | ----------: |
| 官方競賽首頁    |      每 6 小時 |
| 已開放報名競賽   |      每 3 小時 |
| 距截止 14 天內 |      每 1 小時 |
| 大學公告頁     |     每 12 小時 |
| 國際平台      | 每 6 至 12 小時 |
| 已截止競賽     |       每 7 天 |
| 年度固定競賽    | 預估開放前每 6 小時 |

所謂「網站一有變動馬上更新」，如果對方沒有 webhook，本質上還是輪詢。

> 最快每小時發現，不是真正毫秒級即時。

除非來源本身提供：

* RSS

* Webhook
* Email 訂閱
* Sitemap lastmod

這些才比爬蟲更乾淨。

# 變動偵測不能只比整頁

建議保存三種版本：

```ts
raw_html_hash
normalized_text_hash
structured_fields_hash
```

用途：

* `raw_html_hash`：整頁有沒有改
* `normalized_text_hash`：排除樣式、空白、導覽列後有沒有改
* `structured_fields_hash`：競賽重要資料有沒有改

例如網站換了首頁圖片：

```text
raw_html_hash       changed
normalized_text     unchanged
structured_fields   unchanged
```

那就不通知。

如果截止日從 7/31 改到 8/15：

```text
structured_fields.deadline changed
```

立刻通知。

這才叫雷達，不然只是 HTML 神經質監控器。

## 對立性視角

這個想法最大的坑，不是爬蟲寫不出來，而是 **資料可靠性**。

### 1. 很多競賽網站結構爛得像考古遺址

常見情況：

* 日期藏在圖片
* 辦法只有 PDF
* 報名連結是 Google 表單
* 獎金寫在附件第 17 頁
* 網頁過期但沒有下架
* 今年頁面沿用去年網址
* 官方粉專比官網更新更快

所以不能只靠 CSS selector。

必須設計：

* selector fallback
* PDF 解析
* 日期合理性檢查
* 年份辨識
* 人工覆核佇列

### 2. LLM 可能抽錯欄位

例如：

> 總獎金 100 萬

模型可能誤判成：

> 第一名 100 萬

這差很多。

所以要保存：

* 原文證據
* 來源段落
* 信心分數
* 人工確認狀態

每個欄位最好都能點回原文，不然 AI 島會變成「有自信地報錯截止日」的高科技地雷。

### 3. 不是所有網站都適合高頻爬

要尊重：

* robots.txt
* rate limit
* 使用條款
* 反爬機制

先找 API、RSS、sitemap、Email，再用爬蟲。
爬蟲應該是最後手段，不是見網站就拿鏟子挖。

## 我想到一個我覺得比前面都重要的功能

不要只有「作品檔案」，而是建立一個**能力圖譜（Capability Graph）**。

系統不是只知道你有一個網站，而是知道：

* 技能：Python、React、設計、影片剪輯
* 資源：公司、團隊、GitHub、作品集
* 身分：學生、個人、新創
* 目標：創業、得獎、升學、求職
* 作品：網站、APP、論文、歌曲…

然後把每個競賽也拆成相同的能力需求。

推薦就不是「猜你適合什麼」，而是**比對「你目前擁有什麼」和「競賽需要什麼」**。

這樣推薦就有依據，而且會隨著使用者新增作品、技能或經歷，自然越來越準。這會比單純靠 AI 猜測可靠得多，也更容易讓使用者信任。



你想到的全加上 分層可以免費跟收費

## 3. AI 配對組隊

使用者可以設定：

* 缺前端
* 缺設計
* 缺 PM
* 缺行銷

---

## 4. 個人成長時間軸

不是只有參賽紀錄，而是：

> 學習 → 建作品 → 投競賽 → 得獎 → 創業 → 求職

形成完整履歷。

---

我認為**機會島**最大的價值，不是在於「收錄最多競賽」，而是在於它能回答一個更重要的問題：

> **「以我現在的能力、作品和目標，下一步最值得把握的機會是什麼？」**

如果能做到這點，它就不是一個資料庫，而是一個真正能陪伴使用者成長的 AI 機會平台。
